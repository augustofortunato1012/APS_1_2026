# AutoService

REST API and web application for managing automotive workshop clients and their vehicles.

AutoService is an academic project built with Node.js, TypeScript, Express, PostgreSQL, and Supabase. It provides a REST API and a web interface for managing workshop clients and vehicles.

## About the Project

Automotive workshops need to organize client information and the vehicles associated with each client. AutoService centralizes these records through a REST API connected to PostgreSQL using Supabase.

The system has two main entities: `Client` and `Vehicle`. A client can own multiple vehicles, and each vehicle belongs to one client.

## Main Features

- Client and vehicle management with complete CRUD operations
- UUID identifiers and PostgreSQL persistence through Supabase
- Client-to-vehicle relationship with cascade deletion
- Backend input validation and duplicate prevention
- Brazilian mobile phone and license plate validation
- Vehicle brand and model suggestions, with compatibility validation for known entries
- Dynamic vehicle year suggestions and model-specific minimum years
- Dashboard statistics and recent records based on API data
- Responsive web interface
- JSON responses and appropriate HTTP status codes
- Environment-based backend configuration

## Architecture

The backend follows a straightforward request flow:

```text
HTTP Request
		 |
		 v
	 Route
		 |
		 v
 Controller
		 |
		 v
	Supabase
		 |
		 v
 PostgreSQL
```

- **Models** define the `Client` and `Vehicle` entity structures.
- **Controllers** handle application logic, validation, and database operations.
- **Routes** map HTTP methods and paths to controller operations.
- **Config** loads environment variables, configures Supabase, and provides the vehicle catalog.

## Data Model

### Client

| Field | Type | Description |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `name` | VARCHAR(120) | Client name |
| `email` | VARCHAR(150) | Required, unique email address |
| `phone` | VARCHAR(20) | Brazilian mobile phone number |
| `active` | BOOLEAN | Client status; defaults to `true` |
| `created_at` | TIMESTAMPTZ | Record creation timestamp |
| `updated_at` | TIMESTAMPTZ | Most recent update timestamp |

### Vehicle

| Field | Type | Description |
| --- | --- | --- |
| `id` | UUID | Primary key |
| `client_id` | UUID | Required reference to the owning client |
| `brand` | VARCHAR(80) | Vehicle brand |
| `model` | VARCHAR(80) | Vehicle model |
| `year` | INTEGER | Vehicle model year |
| `license_plate` | VARCHAR(10) | Required, unique Brazilian license plate |
| `active` | BOOLEAN | Vehicle status; defaults to `true` |
| `created_at` | TIMESTAMPTZ | Record creation timestamp |
| `updated_at` | TIMESTAMPTZ | Most recent update timestamp |

## Relationship

```text
Client 1 -------- N Vehicle
```

`vehicles.client_id` references `clients.id`. The foreign key uses `ON DELETE CASCADE`, so deleting a client also deletes its associated vehicles.


## REST API

Base URL: `http://localhost:3000/api`

### Client Endpoints

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | `/api/clients` | List clients |
| GET | `/api/clients/:id` | Get a client by ID |
| POST | `/api/clients` | Create a client |
| PUT | `/api/clients/:id` | Update a client |
| DELETE | `/api/clients/:id` | Delete a client and its vehicles |
| GET | `/api/clients/:id/vehicles` | List vehicles belonging to a client |

Example request to `POST /api/clients`:

```json
{
	"name": "John Silva",
	"email": "john@example.com",
	"phone": "(41) 99999-9999",
	"active": true
}
```

### Vehicle Endpoints

| Method | Endpoint | Description |
| --- | --- | --- |
| GET | `/api/vehicles` | List vehicles |
| GET | `/api/vehicles/:id` | Get a vehicle by ID |
| POST | `/api/vehicles` | Create a vehicle |
| PUT | `/api/vehicles/:id` | Update a vehicle |
| DELETE | `/api/vehicles/:id` | Delete a vehicle |

Example request to `POST /api/vehicles` (replace `CLIENT_UUID` with an existing client's UUID):

```json
{
	"client_id": "CLIENT_UUID",
	"brand": "Honda",
	"model": "Civic",
	"year": 2020,
	"license_plate": "ABC1D23",
	"active": true
}
```

## HTTP Status Codes

| Code | Meaning | Typical use |
| --- | --- | --- |
| `200` | OK | Successful retrieval or update |
| `201` | Created | Resource created |
| `204` | No Content | Resource deleted successfully |
| `400` | Bad Request | Invalid input or invalid relationship |
| `404` | Not Found | Requested resource does not exist |
| `409` | Conflict | Duplicate email or license plate |
| `500` | Internal Server Error | Unexpected server or database error |

## Validation Rules

The web interface provides input masks and suggestions to assist users. The backend performs the definitive validation, including when requests are sent directly through Thunder Client or another HTTP client.

### Clients

- **Name:** required, trimmed, cannot be blank or contain only numbers.
- **Email:** required, basic format validation, trimmed, normalized to lowercase, and unique.
- **Phone:** Brazilian mobile number with 11 digits, a valid DDD, and the mobile prefix `9`; the frontend applies a mask.
- **Status:** must be a boolean when provided.

### Vehicles

- **Owner:** `client_id` must be a valid UUID for an existing client.
- **Brand:** required; catalog suggestions are available, and manual entry is supported.
- **Model:** required; suggestions depend on the selected brand, and manual entry is supported.
- Known brand/model mismatches are rejected. Unknown brands or models are accepted when structurally valid; the catalog is not a complete automotive database.
- **Year:** must be an integer from 1900 through the current year plus one. Confirmed models use their model-specific minimum year.
- **License plate:** accepts the old Brazilian format (`ABC1234`) and Mercosur format (`ABC1D23`); values are normalized to uppercase and must be unique.

Examples of catalog compatibility:

| Brand | Model | Result |
| --- | --- | --- |
| Honda | Civic | Valid |
| Toyota | Corolla | Valid |
| Honda | Corolla | Rejected |
| Toyota | Civic | Rejected |

### Confirmed Vehicle Minimum Years

| Brand | Model | Minimum Year |
| --- | --- | ---: |
| Honda | Civic | 1972 |
| Honda | City | 1981 |
| Honda | HR-V | 1999 |
| Toyota | Corolla | 1966 |
| Toyota | Corolla Cross | 2020 |
| Toyota | Yaris | 1999 |
| Toyota | Hilux | 1968 |

The frontend generates year suggestions dynamically, descending from the current year plus one to the applicable minimum. Models without a confirmed minimum use 1900. Users can still enter a year manually, and the backend validates it before saving.

## Dashboard

The dashboard uses API data to show total and active clients and vehicles, active percentages, registrations from the last seven days, vehicle status, and recent clients and vehicles. No random or mock statistics are used.
